# Database Schema

Atlas stores everything in one PostgreSQL database with the TimescaleDB
extension. The reasoning, including why there is no separate metrics store, is
in [ADR-0003](../adr/0003-postgresql-timescaledb.md).

## Migration mechanics

Migrations are `migrations/NNNN_lower_snake_case.sql`, embedded in the binary
so a deployed `atlas-server` can never be paired with the wrong migration set.

**Forward-only. There are no down migrations.** See
[ADR-0007](../adr/0007-forward-only-migrations.md).

Applying migrations:

```bash
atlas-server migrate       # deliberate, one-shot
# or set database.migrate_on_start (default true) and let startup do it
```

### Guarantees

| Guarantee | Mechanism |
| --- | --- |
| Concurrent instances cannot double-apply | Session-level `pg_advisory_lock` held for the whole run |
| A migration is applied and recorded, or neither | Each migration shares a transaction with its ledger insert |
| An applied migration cannot be edited | SHA-256 stored per migration, re-verified on every run |
| A typo'd filename cannot be silently skipped | Filenames must match `NNNN_lower_snake_case.sql` or loading fails |
| A retry resumes cleanly | A failed run leaves earlier migrations applied and recorded |

The advisory lock is released on a live context even when the run's context was
cancelled — otherwise a cancelled migration would leave the lock held until the
connection was reaped, blocking every other instance in the meantime.

### The ledger

`atlas_schema_migrations` is created by the migrator itself rather than by a
migration, since the migrator cannot record migrations before its own table
exists.

| Column | Type | Purpose |
| --- | --- | --- |
| `version` | `bigint` PK | Numeric prefix of the filename |
| `name` | `text` | Descriptive part of the filename |
| `checksum` | `text` | SHA-256 of the file, for tamper detection |
| `applied_at` | `timestamptz` | When it ran |
| `execution_ms` | `bigint` | How long it took |

Inspect it directly:

```sql
SELECT version, name, applied_at, execution_ms
FROM atlas_schema_migrations ORDER BY version;
```

A database that has never been migrated has no ledger, which is a normal
starting state: `Status` and `Pending` report an empty result rather than an
error.

## Applied migrations

### `0001_extensions.sql`

Installs the extensions every later migration depends on. Running first means a
database that cannot support Atlas fails during migration, loudly, rather than
later when a hypertable creation fails.

| Extension | Why |
| --- | --- |
| `timescaledb` | Hypertables, continuous aggregates, compression, and retention policies. A hard requirement — the server image must carry it. |
| `pgcrypto` | `gen_random_uuid()` and digest functions, for identifiers generated by rows that migrations and bulk `COPY` insert without passing through application code. |

## Conventions for future migrations

These are the rules Phase 1 onward follows. They are recorded now so the first
tables are consistent with the last.

### Naming

- Tables: plural `snake_case` — `containers`, `service_dependencies`.
- Columns: singular `snake_case`.
- Timestamps: `timestamptz`, never `timestamp`. A monitoring platform that
  stores naive timestamps produces incident timelines that are wrong across a
  daylight-saving boundary.
- Booleans: positive phrasing — `is_active`, not `is_not_disabled`.
- Foreign keys: `<referenced_table_singular>_id`.
- Indexes: `idx_<table>_<columns>`. Constraints: `<table>_<columns>_<type>`.

### Time-series tables

Every metric and event table is a hypertable, partitioned on its time column:

```sql
CREATE TABLE metric_samples (
    time         timestamptz NOT NULL,
    node_id      text        NOT NULL,
    collector_id text        NOT NULL,
    metric       text        NOT NULL,
    value        double precision NOT NULL,
    unit         text        NOT NULL,
    kind         text        NOT NULL,
    labels       jsonb       NOT NULL DEFAULT '{}'
);

SELECT create_hypertable('metric_samples', by_range('time'));
```

Three rules for these tables:

1. **`node_id` is always present**, including in single-node deployments. The
   schema is multi-node from the start, so Tier 4 needs no data migration. See
   [ADR-0005](../adr/0005-transport-seam.md).
2. **`unit` and `kind` travel with the sample.** Kind determines what
   aggregation is legitimate — averaging a counter is meaningless, and summing
   a gauge across hosts is usually wrong — so recording it lets the query layer
   refuse those mistakes instead of producing a plausible wrong number.
3. **Label cardinality must stay bounded.** Every distinct label combination is
   a distinct series. A PID or a request id as a label will grow the store
   without bound.

### Backward compatibility

Because rollback means running the previous application version against the
newer schema, every migration must work with the release before it:

| Change | How |
| --- | --- |
| Add a column | Nullable, or with a default. Never `NOT NULL` without a default. |
| Remove a column | Two releases: stop reading it, ship, then drop it. |
| Rename a column | Add the new one, write both, backfill, switch reads, drop the old one later. |
| Add an index | `CREATE INDEX CONCURRENTLY`, in its own migration — it cannot run inside a transaction, so it must not share one with other statements. |
| Change a type | Add a new column and migrate, rather than altering in place. |

## Retention and rollups

TimescaleDB provides these natively, and Atlas uses them rather than building
equivalents:

- **Continuous aggregates** for 1-minute, 5-minute, and 1-hour rollups, so a
  query over a month reads pre-aggregated buckets rather than raw samples.
- **Compression** on chunks older than a threshold.
- **Retention policies** to drop chunks past their horizon.

These are defined in the migrations that create their hypertables, arriving in
Phase 1 with the first metric storage.

## Backups

Because there are no down migrations, a restore is the last resort for a
data-destroying mistake — which makes tested backups a hard requirement, not a
nice-to-have. See the [deployment guide](../operations/deployment.md).
